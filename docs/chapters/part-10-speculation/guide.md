# 推测解码与服务闭环：接受了什么，提交了什么

对应 10.1、10.8—10.9、15.1、15.7。前置：自回归采样、KV Cache、请求生命周期。状态：**导读与手算用例已提供；推测实现与 GPU 服务测试待完成**。

吸收 vLLM 第 2、16 讲，SGLang 第 3、14 讲。N-gram、独立 draft、EAGLE、MTP 等仍由 Part 10 的相应章节展开。

## 1. 一轮做三件事

草稿阶段提出若干候选，目标模型验证，接受机制决定可以提交哪些 token。加速的可能性来自一次验证推进多个有效 token；草稿计算、额外 KV 和拒绝后的工作也要计入。

必须区分贪心一致性与随机采样的分布保持。对于经典的自回归草稿拒绝采样，目标分布 p、草稿分布 q，在相同上下文下，候选 x 以 `min(1,p(x)/q(x))` 的概率接受；拒绝时从归一化的正部 `max(p−q,0)` 中补偿采样。q 为零的 token 不会被该草稿分布抽到。

**手算**：p=`[0.6,0.4]`，q=`[0.8,0.2]`。第一个 token 的接受概率 0.75，第二个为 1；拒绝概率为 0.2，补偿分布全部落在第二个 token。因此最终分布为 `[0.6,0.4]`。

树状、自适应和其他提案不必都直接套用这套流程，需核对对应算法。原理来源：[Speculative Decoding 论文](https://proceedings.mlr.press/v202/leviathan23a.html)；具体方法与支持条件查[vLLM 推测解码](https://docs.vllm.ai/en/latest/features/speculative_decoding/)。

## 2. 候选树需要自己的可见性规则

多个候选分支共享前缀，但兄弟分支不能互相泄漏。tree mask 要让每个候选只看到原始历史和自己的祖先。验证可以并行组织，提交仍需选定有效路径。

练习画一棵两层树：根下 a/b，a 下 c/d。列出 c 可以看到的历史，再说明为何不能把候选 `[a,b,c,d]` 当普通因果序列输入。

## 3. KV 预留、计算、提交和回收

假设草稿提出 a/b/c 三个 token，目标接受 a，在 b 处拒绝并补采样 z。逻辑输出可以推进到 a/z；验证已经计算的 b/c 分支 KV 不能作为有效前缀继续用，z 的 KV 则通常需要后续计算。

目标侧和草稿侧状态分开维护；追加长度、已计算长度、可提交长度和预留容量不是一个计数。普通全部接受路径还可能多得到目标模型的 bonus token，要单独说明它是否计入接受率。

与图执行、异步调度、APC 或混合模型组合时，检查未接受分支、在途输出及状态回滚。不能因为最终文本“看起来合理”就判定缓存正确。

## 4. 接受率高为什么仍可能慢

| 观察项 | 回答的问题 |
| --- | --- |
| 接受草稿数 / 提出草稿数 | 候选有多少被采用 |
| 每轮接受草稿数 | 一次验证平均推进了多少草稿位置 |
| 有效输出 token 数 | 是否加上补偿/bonus，并扣除停止边界 |
| 草稿 + 验证 + 状态维护时间 | 为推进这些 token 支付多少成本 |
| TTFT/TPOT/Goodput | 最终用户体验是否改善 |

假设无推测每 token 10 ms，推测每轮共 30 ms、有效推进 2 token，则平均 15 ms/token，反而更慢。这里是数学例子；真实 batch、负载和输出长度变化还会影响结果。

## 5. 把算法放回服务生命周期

设计以下场景，每项保存请求 ID、有效输出、停止原因和资源变化：

- 输出预算小于最大草稿长度，不能越过用户限制返回额外 token。
- EOS/停止条件落在接受前缀内部；后续 token 不应被直接作为内容提交。
- 客户端在草稿或验证中途取消；回收时考虑在途计算。
- 流式 chunk 合并多个 token，不能据 chunk 数统计接受 token。
- 同一模型在不同并发下运行，随机输出不要求逐字相同；贪心比较和分布/质量比较分别设计。

SGLang 的 TokenizerManager/DetokenizerManager 与 vLLM 的引擎/输出处理对象各有职责，类名不混用。逐项检查服务接口和错误处理，不能只做离线单请求的 token 比较。
