# 2.5 练习与参考答案

[正文](README.md) · [实验](lab.md)

先手算，再使用实验快照核对。以下 8 组问题分别检查地址、空间、可见性和回收，不要求先编写 GPU 算子。

## 1. 地址改变，位置是否改变

`B=2`，某请求块表为 `[2,0,3]`，`R=L=6`。列出位置 0—5 的物理 slot。位置 5 的 RoPE 或位置嵌入应该使用 5 还是物理 slot？

<details>
<summary>参考答案</summary>

slot 依次为 `[4,5,0,1,6,7]`。位置 5：逻辑块 `5//2=2`，物理块 `table[2]=3`，偏移 1，slot 为 7。位置编码仍用逻辑位置 5；用 7 会让计算依赖分配器恰好分到了哪里。

</details>

## 2. 三类空间

`B=4、R=9、L=5`。分配几块？有效、尚未写入的预留和取整尾部各有几个位置？`gather(upto=6)` 是否允许？能直接追加 5 个位置吗？

<details>
<summary>参考答案</summary>

分配 `ceil(9/4)=3` 块，即 12 个 slot。有效 5、未来预留 4、尾部空位 3，合计 12。读取 6 个位置超过 L，拒绝。追加 5 个会令新 L=10 超过 R=9，也拒绝；不能把第三块剩余空间当作未经预留即可使用的地址。先把 R 增长到至少 10，此时不需要新增物理块，再追加。

</details>

## 3. GQA 的内存账目

两层模型，每层 3 块，`B=4、Hq=8、Hkv=2、D=8`，存储 float32。K/V 池载荷多少字节？如果错误使用 Hq 会高估几倍？这包含 Attention 的 gather 副本吗？

<details>
<summary>参考答案</summary>

`2 × 2 × 3 × 4 × 2 × 8 × 4 = 3072` 字节，第一个 2 表示 K+V，第二个 2 表示层数。使用 Hq 会高估 `8/2=4` 倍。该公式只包含两个池张量的元素载荷，不包括 gather、中间分数、模型参数和元数据。

</details>

## 4. 等待还是失败

池有 3 块、`B=4`，两个请求均 `P=3、N=3`。A 进入后 B 应进入、等待还是失败？如果把 A/B 的 N 都改成 2，又会怎样？

<details>
<summary>参考答案</summary>

原来每个 `R=5`，取整为 8 个 slot。A 占两块，剩一块，B 等待；不是模型错误，也不是 B 永远无法运行。N=2 时每个 `R=4`，各占一块，物理容量允许二者同时活跃；实际是否同轮执行还受 `max_running` 与该轮输入 token 预算约束。

把这个变体加入 `examples/paged_schedule.py` 时，不能保留“必须 6 轮”的原断言；应先依据负载重新计算期待的计划。

</details>

## 5. 用旧数据构造一个可见的错误

旧请求释放一个含两个位置的块，尾部 V 为 `[99,99]`。新请求只写入 `V=[3,7]`，query 是 `[0,0]`。解释正确输出和错误读取整个块的输出。清零旧尾部能修复读取范围错误吗？

<details>
<summary>参考答案</summary>

正确只读一个位置，softmax 为 `[1]`，输出 `[3,7]`。读两个位置时，两个分数都是 0，权重各 1/2，得到 `[51,53]`。即使旧尾部清零，错误输出也会是 `[1.5,3.5]`，并未修好；根因是归一化包含了不属于有效前缀的位置。运行 `--case reuse` 可观察旧尾部保留与新前缀可见两件事同时成立。

</details>

## 6. 存储有效不等于因果可见

把整个三位置 prompt 的 K/V 一次写完，L=3。现在要计算第 0 个 query，直接调用 `attention(handle, q)` 会有什么问题？如何用本节 API 表达正确范围？

<details>
<summary>参考答案</summary>

默认读取全部 L 个位置，会让第 0 个 query 看见位置 1、2，产生未来信息泄漏。调用 `attention(handle, q, upto=1)`；位置 i 的 query 使用 `upto=i+1`。若输入是一段带历史偏移的 chunk，范围还要加上 chunk 起始的逻辑位置，不能每个 chunk 都从 0 重新计数。

`PagedTinyRunner` 当前逐位置 append 后立即计算，因此不需要再显式缩短可见范围。批量写入的改动必须同时修改读取逻辑。

</details>

## 7. 两种失败能承诺相同的回滚吗

A 已有一块，尝试增长时空闲块不足；另一种情形是 append 写 K 成功、写 V 时发生异常。分别说明哪些状态必须保持不变。为什么第二种情形不能笼统称为“所有写入原子回滚”？

<details>
<summary>参考答案</summary>

容量不足发生在提交分配之前，块表、R、L、空闲块集合和原有 K/V 都不应改变。append 的输入验证失败也在写入之前。

底层复制中途失败时，尚未提交范围的 K 可能已变，但 L 仍然保持原值，所以读路径不会看到半写入结果。它没有恢复所有物理字节。直接操作 store 的调用方需要决定重试或关闭；本节引擎会把异常请求收尾、关闭上下文并归还全部块。不能把“有效前缀的提交边界”扩大成不存在的物理事务保证。

</details>

## 8. 为下一节找出缺少的机制

现在让两个请求共享同一个前缀块。A 先结束，如果原样调用本节 release，把块直接放回空闲池，会发生什么？只加引用计数是否就能安全地让两者向同一个未满块追加？

<details>
<summary>参考答案</summary>

B 还要读取该块，块却可能已经分给 C 并被覆盖。至少需要引用计数，最后一个使用者结束后才能进入相应的可回收状态；缓存复用策略还要区分没有活跃引用和可以立即丢弃的内容。

引用计数只解决生存期。两个请求向同一未满块写不同 token 仍会互相覆盖，需要明确可共享边界与写时复制等策略，还要保证前缀匹配对应相同计算条件。2.6 将讨论这些问题；本节测试仍坚持一请求独占块，不提前声称支持前缀复用。

</details>
