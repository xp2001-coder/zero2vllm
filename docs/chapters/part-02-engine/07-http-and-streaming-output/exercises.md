# 2.7 十四组练习与参考答案

[正文](README.md) · [实验页](lab.md)

先写自己的判断，再展开答案。这里的输出 token 都是数字 ID；除特别说明外，采用本节单进程、单事件循环的实现。

## 1. 一条请求里哪些是输入，哪些是协议描述

客户端向 127.0.0.1:8000/generate 发送 POST，带 `Content-Type: application/json`，以及 `prompt_ids` 和 `max_new_tokens`。依次解释主机、端口、路径、方法、请求头和请求体。

<details>
<summary>参考答案</summary>

主机指当前电脑；端口选择这台电脑上的监听服务；路径选择应用入口；POST 表示提交一份请求。`Content-Type` 描述请求体的编码格式，`prompt_ids` 和 `max_new_tokens` 才是模型请求参数。把 `Content-Type` 写在 JSON 对象里，不能替代 HTTP 请求头。

</details>

## 2. 算出事件序号

最多输出 3 项，生成 [12,3,8]。写出事件种类、`seq` 与 token 的 `index`。若最大输出为 0，又是什么顺序？

<details>
<summary>参考答案</summary>

正常为 `accepted`(`seq`=0)、token(`seq`=1,`index`=0)、token(`seq`=2,`index`=1)、token(`seq`=3,`index`=2)、`done`(`seq`=4)。`seq` 包含接受和终态事件；`index` 只统计输出位置。零输出为 `accepted`(`seq`=0) → `done`(`seq`=1)，没有前向或 KV 预留。

</details>

## 3. 一次读取是不是一条完整事件

同一条事件被网络拆成 1 字节、7 字节或一次全部读到，应该得到几个不同答案？为什么不能对每次读取直接 `json.loads`？

<details>
<summary>参考答案</summary>

只要最终字节完整且顺序相同，恢复的事件也必须相同。读取块可能只有字段名的一部分，可能包含半条 JSON，也可能同时包含多条事件。要先累计字节、按换行读取字段、按空行提交帧，再解析 data 中的 JSON。中文 UTF-8 字节也可能被拆开，因此不能对不完整字符随意使用忽略解码错误的方式。

</details>

## 4. HTTP 200、done 与连接关闭是不是同一回事

服务返回 200，客户端读到 token 12，之后连接关闭。可以认为模型只生成了一项并正常结束吗？

<details>
<summary>参考答案</summary>

不可以。200 说明成功类型的响应已开始；token 说明收到了一项增量结果；缺少 `done` 或 `error` 时无法判断服务端是否按协议完成。可能是网络中断、进程退出或响应被截断。客户端应把它标记为不完整，并保留已经读到的部分结果，不能伪造一个成功终态。

</details>

## 5. async 是否会自动并行计算

把原同步前向外面套一层 `async def`，会不会让两个请求在两个 CPU 核或两张 GPU 上自动同时计算？为什么循环中还需要明确让出执行机会？

<details>
<summary>参考答案</summary>

不会。`async` 描述协程的暂停与等待；同一个事件循环的 Python 同步代码仍按执行顺序占用该线程。一个长时间不让出的前向会拖延发送、取消和超时检查。`await` `asyncio.sleep(0)` 在请求之间给其他任务调度机会，但不会把前向搬到别的线程，也不会合成张量 batch。

</details>

## 6. async for 中 break 之后，谁关闭请求

你从异步生成器读到第一项就 `break`。为什么示例还使用 `aclosing`？如果把 `finally` 中的 `detach` 删掉，可能留下什么？

<details>
<summary>参考答案</summary>

`break` 只说明消费者退出循环，不能依赖它自动及时关闭所有上游资源。`aclosing` 明确调用异步生成器的关闭过程，使 `finally` 及时执行。删掉 `detach` 后，请求可能继续运行、持有 KV 或在满队列上滞留；即使最终由超时回收，也不再是这个示例要求的及时收尾。

</details>

## 7. 容量为 2，为何能生成 3 项

A 的第一次 token 发送不返回，此时输出队列已满，容量为 2。画出三项输出分别在哪里。能据此推断客户端已经看到了第一项吗？

<details>
<summary>参考答案</summary>

事件 1 已由发送协程取出，正在等待 `send`；事件 2、3 在队列中；第四次生产暂缓。队列上限不包含那条在途事件。因此可以有 Q+1 条尚未完成发送的输出事件，终态还有独立位置。发送尚未完成自然不能证明客户端收到；即使 `send` 返回，也只是传输交接，仍不是用户显示确认。

</details>

## 8. 每请求一条队列，为什么仍可能拖住全局

如果把驱动器的 `put_nowait` 改成 `await` A.queue.put，A 不消费时会有什么影响？怎样在本节模型下避免？

<details>
<summary>参考答案</summary>

共享驱动器可能一直等在 A 的入队操作，轮不到 B。应在生产前检查该请求队列是否有空位，满时暂缓它，继续处理其他有资格的请求。本节只有一个生产驱动器，检查、同步前向和入队之间没有切换到另一个生产者，因此可以使用 `put_nowait`。多生产者设计需要重新建立这个并发约束，不能机械照搬。

</details>

## 9. 暂缓生产是否已经归还 KV

A 队列满后不再前向。此时它的 KV、运行名额、开放流名额分别还在不在？如果所有运行名额都被慢请求占用，B 一定能继续吗？

<details>
<summary>参考答案</summary>

只要 A 尚未终止，KV 和运行名额仍在；只要流尚未收尾，开放流名额也仍在。B 需要可用运行名额和实际 KV 额度。如果都被慢请求占用，它仍会等待，直到完成、取消或超时归还资源。满队列暂停解决输出无限增长与全局入队阻塞，并不自动实现缓存换出和抢占。

</details>

## 10. error 为什么放在单独的终态槽

输出队列满时模型发生异常，若终态也必须阻塞入队才能处理，会出现什么问题？当前顺序是否会丢掉之前已经提交的 token？

<details>
<summary>参考答案</summary>

资源回收可能被满队列拖住，而客户端恰好已经不再消费，形成长时间滞留。当前先由引擎结束请求并归还 KV，把 `error` 放入独立终态槽。连接仍可用时，先发已经排队的输出，再发 `error`；连接断开时清空待发队列，但服务端仍记录已提交输出，不谎称客户端全收到。

</details>

## 11. 取消共享请求 A，怎样证明 B 没被误伤

A、B 共享 2.6 的前两个物理块。A 提前断连，B 继续输出。至少核对三项证据，并解释为什么不应该把整个池 reset。

<details>
<summary>参考答案</summary>

核对 A 终态和其额度归还；共享块 refs 从 2 降到 1；B 后续输出与独立参考一致；最终两者都结束时活跃引用归零。reset 整个池会破坏仍被 B 使用的内容或违反重置前置条件。取消只撤销 A 的使用权，不拥有“删除所有相同前缀”的权利。

</details>

## 12. 区分四种超时

请求体迟迟收不完整、请求一直等待运行名额、输出队列持续满、发送调用一直不返回，分别对应哪个超时？`request_timeout` 是否在每个 token 之后重新计时？

<details>
<summary>参考答案</summary>

依次为 `body_timeout`、`request_timeout`、`slow_timeout`、`send_timeout`。`request_timeout` 从进入服务管理开始，包含排队，不逐 token 续期。`slow_timeout` 只观察连续满队列，消费后重新计时。同步前向长时间占用事件循环时，检查会延迟，因此这些期限不提供任意位置强制中断计算的能力。

</details>

## 13. 为什么服务器记录里有 2 项，客户端只有 1 项

客户端读到第一项就关闭，报告显示引擎提交两项，`send_completed_tokens` 可能也是两项。是否必然是缓存或事件顺序出错？

<details>
<summary>参考答案</summary>

不必然。引擎、服务器发送与客户端读取是不同的边界，关闭传播期间还可能提交和交出额外输出。需要进一步核对事件序号、客户端是否主动提前退出、引擎是否及时进入终态、KV 是否归还。不能把服务器交出的数量当成客户端实际显示的确认，也不应据此回写伪造客户端记录。

</details>

## 14. 给一次服务修改写验收条件

有人说“curl 看起来逐字输出，所以流式服务完成了”。请补充至少六项验收，并指出哪类实验必须区分真实网络与受控边界。

<details>
<summary>参考答案</summary>

至少包括：输出与完整重算一致；多个请求不串流；事件序号和终态数量正确；非法输入在生成前被拒绝；真实客户端断连后额度归还；满队列时生产受限且有容量的同伴继续；发送超时和模型异常后不泄漏；关闭服务不留下任务；分字节解析能处理中文和截断。

真实本机连接用于检查 HTTP、读取与断连集成；受控 ASGI `send` 用来确定性地制造发送阻塞。不能把后者的人工等待说成真实网速、GPU 延迟或服务吞吐测试。

</details>
