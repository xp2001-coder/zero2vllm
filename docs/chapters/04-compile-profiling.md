# 编译、图执行与 Profiling：让优化结论可解释

对应 8.1—8.4、17.1—17.3、17.6。前置：请求链路、基本 kernel 概念。状态：**源码导读与实验方案已提供；GPU 测量待执行**。

吸收 vLLM 第 9、17、18、20 讲，SGLang 第 11—13 讲与逐项测试手册。

## 1. 两层编译和图回放

第一层从 PyTorch 模型出发：Dynamo 捕获 Python 中的 Tensor 计算，形成 FX 图，经后端和 Inductor 等阶段生成执行代码。guards 检查运行条件，输入变化可能触发特化、重新编译或断图。

第二层以 Triton kernel 为例：前端生成 IR，经过设备相关的布局与 lowering，最终生成目标代码。不同后端的后续编译阶段可能不同；不要把 NVIDIA 的 PTX 作为所有平台的共同终点。

CUDA Graph 则捕获可回放的设备工作序列，减少重复提交开销。模型编译、手写融合和 Graph replay 可以组合，但它们的对象、缓存键和耗时不相同。阅读 [vLLM 编译设计](https://docs.vllm.ai/en/latest/design/torch_compile/)及[Triton 编译器](https://github.com/triton-lang/triton/tree/main/python/triton/compiler)时分别画图。

## 2. 动态请求如何进入相对稳定的图

把真实批次映射到可捕获的形状，预留稳定 buffer，更新其中的数据，再重放图。分桶和 padding 扩大了可复用范围，也增加计算或内存开销。

不能笼统说“开启图就完全不能变化”：捕获图有约束，而引擎可以选择不同图或回退。vLLM 区分配置模式和运行时的 `NONE/PIECEWISE/FULL`，实际模式还与批次组成、Attention 后端等有关。[CUDA Graph 设计](https://docs.vllm.ai/en/latest/design/cuda_graphs/)

记录表中至少区分：**用户请求模式、解析后的有效配置、本轮实际模式**。启动参数里出现 `FULL` 不足以证明所有批次都走完整图。

## 3. 编译与图执行的实验格子

下面是实验设计，只有所选版本支持的格子才运行。用独立配置控制编译与 graph；如某配置联动关闭多项优化，应把变化如实记下。

| 编号 | 编译 | 图执行 | 主要回答 |
| --- | --- | --- | --- |
| C0 | 关闭/基线 | 关闭 | 未启用这些优化时的行为 |
| C1 | 开启 | 关闭 | 编译、融合与生成代码的影响 |
| C2 | 与 C1 相同 | 分段图 | 分段回放的增量影响 |
| C3 | 与 C1 相同 | 完整图或混合模式 | 更大捕获范围的收益、成本和回退 |

每格报告冷启动、首次编译/捕获、预热后稳态、显存和正确性。runner 版本、模型、量化方案、请求序列保持固定；MRV2 另按[请求导读](01-request-lifecycle.md)的四格实验处理。

## 4. 先量性能，再单独抓 trace

1. 固定模型和数据，运行无 profiler 的基线与单项实验；保存完整请求结果和失败。
2. 各取负载相同的区间做 trace。记录 rank、阶段、实际请求数、token 数、shape 和图模式。
3. 先定位关键路径：排队、CPU 准备/提交、设备计算、通信、拷贝、等待。
4. 再下钻高占比算子，按语义、shape、dtype 对齐比较。
5. 解释改动影响，并回到无 profiler 的整体测量验证。

工具入口：[vLLM Profiling](https://docs.vllm.ai/en/latest/contributing/profiling/)。A100 可按条件使用 PyTorch Profiler/Nsight；C500 使用实际配套工具，不假定 NVIDIA 工具可以直接替代。

## 5. 一个容易误判的 trace 例子

教学假设：基线某 GEMM 调用 100 次，每次 20 μs，累计 2 ms；实验调用 50 次，每次 25 μs，累计 1.25 ms。

累计时间下降 37.5%，但单次时间增加 25%。这可能是 batching 或调度变化带来的结果，不能写成“kernel 快了 37.5%”。还要比较同 shape 的调用，检查减少的工作是否相同、正确性是否保持。

多流的两个 kernel 分别运行 2 ms 和 3 ms、完全重叠 2 ms 时，累计是 5 ms，覆盖的墙钟区间是 3 ms。累计 kernel 时间相加既不是端到端时延，也不是 GPU 利用率。看到空隙后还需查依赖，不能立即归因给 CPU。

## 6. 负载、分位数与 Goodput

按[实验规范](../experiments.md)的 W0—W7 从 smoke 扩展到 prefill、decode、共享前缀和混合长度。

- 有限到达率与固定并发回答不同问题；客户端并发限制可能让实际发送率低于设定值。
- 三轮分别报告结果；取中位数表示重复实验稳定性。合并 P99 需要原始请求样本，不能平均三次 P99。
- 成功吞吐与满足延迟目标的 Goodput 分开；超时和失败不能消失在分母中。
- 输入目标长度在模板和 Tokenizer 后检查，输出上限与实际长度分开。

## 7. 四类算子的优化记录

| 对象 | 必须对齐的条件 | 消融方向 |
| --- | --- | --- |
| Attention | query/KV 长度、heads、dtype、布局、命中情况 | 后端、分页、分区、KV Q/DQ |
| Linear/GEMM | M/N/K、stride、W/A 格式、布局 | 显式 DQ、融合 DQ、tile、预打包 |
| MoE | 每专家 token 分布、top-k、路由与通信 | permute、grouped GEMM、负载均衡 |
| Norm/RoPE/量化 | 有效 token、尾部、缩放与融合边界 | 访存、kernel 次数、误差 |

MACA 环境变量逐项验证：先确认当前版本确实读取该变量，再观察执行分支变化。资料中的 C600 多卡开关保留为排查线索，C500 选择需要独立证据。
